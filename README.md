# Визуализатор графа зависимостей Alpine Linux APK

**Практическая работа по дисциплине «Конфигурационное управление», вариант №23.**

Проект — небольшое CLI-приложение на C++17. Оно читает настройки из TOML,
получает метаданные Alpine APK из `APKINDEX`, строит граф зависимостей
итеративным DFS и формирует PlantUML, SVG и ASCII-дерево.

## 2. Настройки TOML

Приложение принимает пять параметров. Все они обязательны.

| Параметр | Тип | Назначение |
|---|---|---|
| `package` | строка | Имя анализируемого пакета |
| `repository` | строка | Путь к тестовому файлу или URL `APKINDEX.tar.gz` |
| `test_mode` | `true` / `false` | Выбор тестового или реального репозитория |
| `ascii_tree` | `true` / `false` | Включить ASCII-дерево |
| `max_depth` | целое число 0–100 | Максимальная глубина обхода |

Пример `config.toml`:

```toml
package = "A"
repository = "test_repo.txt"
test_mode = true
ascii_tree = true
max_depth = 3
```

Если `test_mode = true`, `repository` — путь к файлу тестового графа.
Относительный путь считается от каталога, в котором лежит TOML-файл.
Если `test_mode = false`, `repository` — прямой URL к файлу
`APKINDEX.tar.gz`, например:

```toml
package = "zlib"
repository = "https://dl-cdn.alpinelinux.org/alpine/v3.19/main/x86_64/APKINDEX.tar.gz"
test_mode = false
ascii_tree = true
max_depth = 3
```

Конфигурационный загрузчик поддерживает используемое проектом подмножество
TOML: плоские пары `ключ = значение`, строки в двойных кавычках, логические
значения, целые числа и комментарии `#`. Таблицы и массивы не используются.

## 3. Сборка и запуск

Нужны C++17-компилятор, CMake и Make/Ninja. Проект проверен в Linux;
на Windows его удобно запускать через WSL. Для реального репозитория
дополнительно нужны стандартные консольные программы `curl` и `tar`.

```bash
chmod +x run.sh
./run.sh
```

Скрипт собирает проект, запускает автоматические тесты и затем запускает
визуализатор. Можно указать другой конфигурационный файл:

```bash
./build/visualizer examples/config_X.toml
```

Отдельная сборка и тестирование:

```bash
cmake -S . -B build
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Приложение сохраняет `graph.puml` и `graph.svg` в текущем каталоге.
В графической Linux-сессии SVG автоматически открывается через `xdg-open`.
В остальных случаях файл можно открыть браузером или просмотрщиком SVG.

## 4. Тестовый репозиторий

Формат файла: одна запись на строку — `ПАКЕТ: ЗАВИСИМОСТИ`.
Имена тестовых пакетов должны состоять из больших латинских букв.
Все упомянутые зависимости должны быть объявлены отдельными строками.

В `test_repo.txt` находятся несколько независимых сценариев:

- `A` — разветвлённый граф с общей зависимостью `F`;
- `X` — небольшая ациклическая цепочка с ветвлением;
- `P` — цикл `P -> Q -> R -> P`;
- `U -> A` и `V -> U` — проверка транзитивных обратных зависимостей.

Для трёх примеров выполните:

```bash
./build/visualizer examples/config_A.toml
./build/visualizer examples/config_X.toml
./build/visualizer examples/config_P.toml
```

Для повторной генерации демонстрационных файлов:

```bash
./examples/generate_examples.sh
```

## 5. Алгоритмы

Граф строится итеративным DFS с использованием собственного стека.
Рекурсия не используется. Для каждой вершины хранится минимальная найденная
глубина. Если позднее вершина найдена по более короткому пути, она раскрывается
повторно. Это необходимо для корректного ограничения глубины. Цикл прекращается,
когда вершина уже была обработана на той же или меньшей глубине.

Глубина корневого пакета равна нулю. При `max_depth = 2` выводятся вершины на
уровнях 0, 1 и 2; зависимости вершин уровня 2 дальше не раскрываются.

Обратный граф формируется перестановкой каждого ребра `пакет -> зависимость`
в ребро `зависимость -> пакет`. Затем применяется тот же итеративный DFS.

## 6. Получение Alpine APKINDEX

Реальный режим загружает архив по URL командой `curl` и извлекает текстовый
`APKINDEX` командой `tar`. Менеджер пакетов `apk` и сторонние библиотеки для
получения зависимостей в реализации не вызываются.

Из записей индекса читаются поля:

- `P` — имя пакета;
- `D` — прямые зависимости;
- `p` — дополнительные предоставляемые имена;
- `k` — приоритет провайдера.

Если зависимость указана как предоставляемая возможность, выбирается пакет-
провайдер с наибольшим `k`. Из версии в токене зависимости удаляется ограничение,
так как проект строит граф имён пакетов, а не реализует полный APK solver.

Реализация рассчитана на индекс старого формата `APKINDEX.tar.gz` (v2).
Новый формат `Packages.adb` не разбирается.

## 7. Сравнение со штатными средствами Alpine

В Alpine есть штатная команда `apk dot`, которая генерирует граф в Graphviz DOT.
Также `apk info --depends` показывает зависимости, а `apk info --rdepends` —
обратные зависимости. Эти средства используются только для сравнения; программа
не запускает их для получения метаданных.

Результаты могут различаться из-за выбора репозитория и архитектуры, обработки
виртуальных `provides`, приоритетов нескольких провайдеров, ограничений версий
и состояния установленных пакетов. В нашем проекте выбран один URL индекса,
а разрешение виртуальных имён реализовано упрощённо. Поэтому сравнивать нужно
одинаковый репозиторий и одну архитектуру.

Документация:

- [Поля пакета и APKINDEX: apk-package(5)](https://github.com/alpinelinux/apk-tools/blob/master/doc/apk-package.5.scd)
- [Штатная визуализация: apk-dot(8)](https://man.archlinux.org/man/apk-dot.8.en)
- [Информация о зависимостях: apk-info(8)](https://man.archlinux.org/man/extra/apk-tools/apk-info.8.en)

## 8. История этапов Git

В репозитории предусмотрены пять коммитов в формате Conventional Commits:

1. `feat(config): add TOML-based CLI configuration`
2. `feat(apk): parse Alpine APKINDEX dependencies`
3. `feat(graph): build dependency graph with iterative DFS`
4. `feat(graph): add reverse dependency traversal`
5. `feat(output): generate PlantUML, SVG and ASCII tree`

Для публикации в личном Git-сервисе добавьте свой remote и отправьте ветку:

```bash
git remote add origin <URL-ВАШЕГО-РЕПОЗИТОРИЯ>
git push -u origin master
```
